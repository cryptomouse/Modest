# VLA — как это устроено в компиляторе

Карта для тех, кто чинит или дорабатывает массивы переменной длины
(`[n]T`). Правила языка — в [`docs/lang/type/array.md`](../../lang/type/array.md#variable-length-arrays);
здесь — где и как они реализованы.

## Главная идея

**Границы VLA снимаются один раз — там, где выполняется объявление**
(`type`, `var`, `let`), как в C. Дальше размер, `lengthof` и индексация
берут снятое значение, а не перечитывают выражение:

```modest
var k: Nat32 = 10
var a: [k]Int32
k = 0
lengthof(a)     // 10, а не 0
```

Почти всё остальное — следствия этого правила и ограничений бэкендов:
у C нет составных литералов VLA-типа и инициализаторов VLA, а LLVM вообще
не знает VLA-типов — для него это `[0 x T]` плюс размер, посчитанный
вручную.

## Типы: что спрашивать у `TypeArray`

`src/hlir/types.py`

| Что | Значит | Пример: true / false |
|---|---|---|
| `is_vla()` | длина **внешнего** уровня известна лишь при выполнении | `[n]T` / `[3][n]T`, `[]T` |
| `is_runtime_sized()` | размер массива целиком известен лишь при выполнении: VLA на любом уровне массива, но не за указателем | `[n]T`, `[3][n]T` / `*[n]T`, `[n]*T` |
| `contains_vla()` | VLA где угодно, в том числе за указателем | `*[n]T` |
| `frozen_volume` | снятое бэкендом значение границы; если не `None`, работать надо по нему, а не по `volume` | — |
| `slice` | тип среза `a[i:j]`: длина тоже бывает известна лишь при выполнении, но это **не** VLA | — |

Обычно нужен `is_runtime_sized()`: `sizeof`, копирование, нулевой хвост.
`is_vla()` достаточно там, где важен только внешний уровень (`lengthof`).

## Семантика: что запрещено и где

`src/semantic.py`, `src/value/array.py`, `src/hlir/types.py`

- **Только локально.** `do_type_array`: длина времени исполнения вне
  функции даёт `non local VLA are forbidden`. Это касается module-level
  `var`/`const`/`type`, параметров и результата функции, в том числе
  через указатель. Внутри функции при этом функции ставится атрибут
  `stacksave`.
- **Не внутри записи, функционального типа, варианта.** `check_no_vla`
  (зовется из `do_type_record`, `do_type_func`, `do_type_variant`): там
  нет объявления, на котором можно снять границы. Массив массивов
  (`[i][j]T`) и указатель на VLA (`*[n]T`) — можно.
- **VLA и фиксированный массив — разные типы.** `eq_array`: если у одного
  длина известна при компиляции, а у другого нет — типы не равны (кроме
  срезов, см. `slice`). `_array_widening_can` (`src/value/array.py`) не
  дает расширять массив из VLA или в VLA. Копировать их друг в друга
  нельзя — только через срез.
- **Литерал в VLA разрешён.** `value_array_cons` приводит элементы к типу
  элемента, но нулевой хвост не добавляет (длину приемника не знает).

Семантика VLA **не разворачивает**: никаких скрытых `let` для границ.
Modest-бэкенд печатает HLIR обратно в исходник и напечатал бы и их. Всё,
что нужно только для генерации кода, делается в бэкендах (BUG#110).

## Заморозка границ

Обе функции называются `freeze_vla_volumes(t)` и проходят по всем
уровням типа, в том числе через указатели. Уже замороженные уровни не
трогают: у `var a: A` границы уже сняты в `type A`.

**C** (`src/backend/c11.py`): для каждой границы выводится константа, и
её имя записывается в `frozen_volume`:

```c
const uint32_t __a_0 = n;
int32_t a[__a_0];
```

Вызывается из `do_cstmt_var`, `do_cstmt_const`, `do_def_type`. Всё, что
печатает длину, идет через `cvalue_volume(t)`, а она отдаёт
`frozen_volume`, если тот есть. Размер считает
`cvalue_sizeof_type(t)`: для runtime-sized это
`sizeof(T) * __a_0 * ...`.

**LLVM** (`src/backend/llvm.py`): граница вычисляется в SSA-регистр
(`Size`) на месте объявления, регистр записывается в `frozen_volume`.
Вызывается из `print_stmt_var`, `print_stmt_const`,
`print_stmt_def_type`.

## LLVM: размеры и память

- `handleVLA(t)` рекурсивно считает `t.runtimeVolume`,
  `t.runtimeSizeRoots` (размер в корневых элементах) и
  `t.runtimeSizeBytes`. **Он пересчитывает их при каждом обращении и
  ничего не кэширует.** Регистр, посчитанный впервые внутри `if`, не
  доминирует над использованием после `if`, и IR не собрался бы. Границы
  при этом берутся из `frozen_volume`, так что пересчёт — это только
  умножения.
- Память: `alloca <корневой тип>, Size runtimeSizeRoots`
  (`get_array_root()`). Значение VLA в регистре имеет тип `[0 x T]`, и
  `load`/`store` такого значения **ничего не копируют**. Поэтому VLA
  всегда копируется через `memcpy` по адресу.
- Стек: из-за атрибута `stacksave` функция сохраняет указатель стека на
  входе и восстанавливает его перед `return`.
- Временные массивы фиксированного размера (`fctx['slots']`) выделяются
  в entry-блоке: `alloca` в теле цикла увеличивал бы стек на каждой
  итерации. См. `collect_slot_stmts`, `print_slots`.

## Копирование VLA → VLA

`a = b`, `var a: [n]T = b`, `let a = b`

Длины не сравниваются, копируется **размер приёмника**. Это открытый
вопрос: QUESTION#7.

- **C**: `assign_by_memcopy`, то есть
  `memcpy(&a, &b, cvalue_sizeof_type(a.type))`.
- **LLVM**: `is_vla_copy(to, value)` решает, что это копия VLA, и тогда
  `llvm_copy_vla` выполняет `memcpy` по адресу. Литералы и срезы идут
  своим путём. У `let`, заданной литералом, тоже есть `asset`, но живёт
  она в памяти, поэтому `value.is_const()` тоже считается копией.

## Литерал в VLA

BUG#112, BUG#115

`var a: [n]Int32 = [1, 2, 3]`, `a = [[1, 2], [3]]` для `[n][m]T`,
`let b = [n]Int32 [1, 2]`

Построить литерал с типом VLA нельзя ни в C, ни в LLVM. Поэтому:

1. **`vla_literal_type(t, v)`** (`src/hlir/types.py`) вычисляет тип
   литерала его собственной длины. На уровнях с VLA внутри берется длина
   самой длинной строки, короткие строки дополняются нулями:
   `[n][m]Int32` ← `[[1, 2, 3], [4]]` даёт `[2][3]Int32`. Ниже последнего
   уровня с VLA тип элемента берётся из `t` как есть. Функция возвращает
   `None`, если путь не этот: длина известна при компиляции, `v` не
   литерал или пустой `[]`, или строка не литерал (`[r, r]` — BUG#116).
2. Бэкенд строит литерал этого типа, **обнуляет приемник** и на каждом
   уровне копирует **min(L, n)** элементов. Строки за концом VLA
   пропускаются. Так при любом `n` нет выхода за конец ни литерала, ни
   VLA.

- **C** — `assign_vla_literal`, вызывается из `do_assign_array`.
  - Для `[n]T` это одна копия из составного литерала своей длины:
    ```c
    __builtin_bzero(&a, sizeof(int32_t) * __a_0);
    __builtin_memcpy(&a, &(int32_t [3]){1, 2, 3}, sizeof(int32_t) * (__a_0 < 3 ? __a_0 : 3));
    ```
  - Для VLA внутри литерал кладётся во временную переменную, чтобы
    элементы времени исполнения вычислились один раз. Каждая строка
    копируется под своей проверкой (`copy_vla_literal_rows`):
    ```c
    int32_t __literal[3][3] = {{1, 2, 3}, {4}, {x, x + 1}};
    if (0 < __a_0) {
    	__builtin_memcpy(&a[0], &__literal[0], sizeof(int32_t) * (__a_1 < 3 ? __a_1 : 3));
    }
    ```
  - В cshape нет тернарного оператора, поэтому `CValueCond` определён
    прямо в `c11.py`.
  - VLA нельзя инициализировать в объявлении, поэтому `do_cstmt_var` и
    `do_cstmt_const` выводят объявление без инициализатора
    (`dynamic_init`), а потом присваивание. У такой `let` снимается
    `const`.
- **LLVM** — `llvm_copy_vla_literal`, вызывается из
  `print_stmt_var`, `print_stmt_const`, `print_stmt_assign`.
  - Литерал своей формы сохраняется во временный слот. Слоты собирает
    `collect_vla_literal_slot`, ключ — `id(значения)`.
  - Затем `memset` всего приёмника и построчный `memcpy`
    (`llvm_copy_vla_literal_rows`). Для строки за концом VLA размер через
    `select` становится нулевым, ветвлений нет.
  - Ловушка: `do_eval` **всегда** ставит результату `x.type`. Поэтому
    литерал вычисляется из копии значения с подменённым типом
    (`vla_literal_as`). Ставить тип внутри `eval_cons_array`
    бесполезно, его перезапишут.

Почему min(L, n), а не ошибка: что программа должна делать при L ≠ n,
пока не решено (QUESTION#7). min(L, n) выбран как безопасный вариант до
ответа на этот вопрос.

## Открыто

- **QUESTION#7** — копирование VLA ↔ VLA разной длины и литерал не той
  длины. Ответ затронет оба раздела выше.
- **BUG#116** — строка литерала, которая сама VLA-значение (`[r, r]`).
- **UB#1** — срез с границами времени исполнения при несовпадении длин.
